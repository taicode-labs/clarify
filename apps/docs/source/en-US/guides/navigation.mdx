# Configuring the Site

This page brings together the configuration related to the "site experience" in Clarify: top navigation, tabs, the sidebar, theming, multiple languages, the deployment subpath, and information architecture.

For real projects, we recommend expressing reader task paths through configuration rather than directly exposing the repository's directory structure.

---

## Top navigation

Put only a small number of high-frequency entries in the top navigation:

```ts
import { defineConfig } from '@clarify-labs/cli'

export default defineConfig({
  navigation: {
    menus: [
      { label: 'Get Started', page: 'getting-started' },
      {
        label: 'Resources',
        items: [
          { label: 'API Documentation', page: 'features/openapi' },
          { label: 'GitHub', href: 'https://github.com/taicode-labs/clarify' },
        ],
      },
    ],
  },
})
```

| Field | Description |
|------|------|
| `label` | The display text of the nav item; supports multi-language objects |
| `href` | A URL; external URLs are detected automatically |
| `page` | References an MDX page under `source`, without the `.mdx` suffix |
| `items` | Nested menu items; each item supports `href`, `page`, or another `items` array |
| `description` | Optional supporting text shown in expanded menus |
| `icon` | Optional Lucide icon name |

## Tabs and the sidebar

Clarify uses `navigation.tabs` for a top layer of business categorization for the site. Each tab has its own sidebar.

```ts
export default defineConfig({
  navigation: {
    tabs: [
    {
      tab: 'Docs',
      icon: 'BookOpen',
      pages: [
        {
          group: 'Get Started',
          icon: 'Rocket',
          pages: [
            { page: 'getting-started', icon: 'Map' },
            { page: 'guides/writing-content', title: 'Writing Content', icon: 'PenLine' },
          ],
        },
      ],
    },
    ],
  },
})
```

`tabs[].pages` supports two modes:

| Mode | Use case |
|------|----------|
| `'FileTree'` | Small sites or early prototypes, generated directly from the `source` directory |
| Group array | Formal documentation sites, organizing reading paths by user tasks |

Page item types:

| Field | Description |
|------|------|
| `page` | References an MDX page under `source`, without the `.mdx` suffix |
| `openapi` | References an OpenAPI JSON/YAML file under `source` |
| `group` | Creates a collapsible group; its `pages` can contain pages or nested groups |
| `title` | Overrides the page's display title in navigation |
| `icon` | Uses a lucide icon name |

### Nested sidebars

For larger documentation sets, groups can be nested inside a top-level group:

```ts
{
  group: 'Guides',
  icon: 'BookOpen',
  pages: [
    {
      group: 'Authentication',
      icon: 'KeyRound',
      pages: [
        { page: 'guides/auth/setup', title: 'Configure authentication' },
        { page: 'guides/auth/sso', title: 'Single sign-on' },
      ],
    },
    { page: 'guides/deployment', title: 'Deployment' },
  ],
}
```

Nested groups appear as expandable directories in the sidebar. Every ancestor of the current page expands automatically, while other groups can be opened or closed independently. Mobile navigation uses the same structure: expanding a directory keeps the drawer open, and following a page link closes it.

Groups can be nested recursively, but we recommend no more than three visible information levels for easy scanning: a top-level group, one nested group, and pages. Prefer page sections or another tab for deeper structures.

Example OpenAPI entry:

```ts
{
  openapi: 'api.openapi.json',
  title: 'API Reference',
  icon: 'FileJson2',
}
```

## Recommended information architecture

We recommend converging user docs into a small number of core entries:

| Entry | Problem it solves |
|------|------------|
| Getting Started | How to install, create pages, run, and build |
| Writing Content | How to write MDX, organize directories, use frontmatter and components |
| Configuring the Site | How to configure navigation, theme, multiple languages, and paths |
| API Documentation | How to turn OpenAPI into a reference and embed it in tutorials |
| Publishing | How to build, deploy, and output `llms.txt` |
| Reference | Look up fields, commands, and component properties |

Do not make every internal capability its own navigation entry. Details can live in sections of the same task document, or in the reference pages.

## Theming

Clarify currently provides a stable, focused theme configuration: choose a preset first, then override it with a small number of tokens.

```ts
export default defineConfig({
  theme: {
    preset: 'base',
    tokens: {
      colors: {
        primary: '#00D492',
      },
    },
  },
})
```

Current presets:

| Preset | Description |
|------|------|
| `default` | The Clarify brand theme |
| `base` | A neutral theme of black, white, and gray |

Notes:

- You do not need to create a `tailwind.config.js`.
- Light, dark, and system-preference detection are built into the renderer.
- The shipped interface is neutral: the brand color shows up on links, primary buttons, and focus rings. Navigation rails, tab underlines, and selected rows stay grayscale on purpose — flooding them with the brand color is what makes a page look muddy.

### Bringing the brand tint back

If you want the tinted navigation, tabs, and menus back, override the `--clarify-brand-*` layer instead of editing selectors:

```css
:root {
  --clarify-brand-active-background: color-mix(in srgb, var(--clarify-theme-tokens-colors-primary) 12%, transparent);
  --clarify-brand-active-text: var(--clarify-theme-tokens-colors-primary);
  --clarify-brand-tab-indicator: var(--clarify-theme-tokens-colors-primary);
  --clarify-brand-navigation-marker: var(--clarify-theme-tokens-colors-primary);
  --clarify-brand-navigation-icon: var(--clarify-theme-tokens-colors-primary);
  --clarify-brand-search-highlight: var(--clarify-ui-accent-text);
}
```

Every one of these defaults to a neutral value, so overriding two or three of them is enough; the rest keep the default.

Injection goes through a plugin: there is no project-level custom CSS entry yet, and the smallest hook is `html:transform` adding a `<style>` tag to the head.

```ts title="clarify.plugin.ts"
import type { ClarifyPlugin } from '@clarify-labs/cli'

export function brandTintPlugin(): ClarifyPlugin {
  const css = `:root {
    --clarify-brand-tab-indicator: var(--clarify-theme-tokens-colors-primary);
    --clarify-brand-navigation-marker: var(--clarify-theme-tokens-colors-primary);
  }`

  return {
    name: 'brand-tint',
    hooks: {
      'html:transform': (input) => ({
        ...input,
        tags: [...input.tags, { tag: 'style', children: css, injectTo: 'head' }],
      }),
    },
  }
}
```

## Internationalization

After enabling `i18n`, content is organized by locale directories, and routing, navigation, the language switcher, and missing-translation fallback are handled automatically.

```ts
export default defineConfig({
  locales: {
    default: 'zh-CN',
    missing: 'fallback',
    locales: [
      { code: 'zh-CN', label: '简体中文', dir: 'ltr' },
      { code: 'en-US', label: 'English', dir: 'ltr' },
    ],
  },
})
```

Directory example:

<FileTree aria-label="Localized source directory">
  <FileTreeItem name="source" type="folder">
    <FileTreeItem name="zh-CN" type="folder">
      <FileTreeItem name="index.mdx" />
      <FileTreeItem name="getting-started.mdx" />
    </FileTreeItem>
    <FileTreeItem name="en-US" type="folder">
      <FileTreeItem name="index.mdx" />
      <FileTreeItem name="getting-started.mdx" />
    </FileTreeItem>
  </FileTreeItem>
</FileTree>

Routing rules:

| File | Route |
|------|------|
| `source/zh-CN/index.mdx` | `/` |
| `source/zh-CN/getting-started.mdx` | `/getting-started` |
| `source/en-US/index.mdx` | `/en-US` |
| `source/en-US/getting-started.mdx` | `/en-US/getting-started` |

Missing-translation strategies:

| Strategy | Behavior |
|------|------|
| `fallback` | Missing pages generate the corresponding locale route using the default-language content |
| `404` | Missing pages do not generate a route for that language |
| `hide` | Missing pages are not generated; they are also hidden from the automatic file-tree navigation |

Visible text in the configuration supports localization objects, for example:

```ts
{
  label: {
    'zh-CN': '文档',
    'en-US': 'Docs',
  }
}
```

## Deployment subpath

If the site is deployed under a subpath, such as a GitHub Pages project site, configure `routePrefix`:

```ts
export default defineConfig({
  routePrefix: '/my-repo/',
})
```

Clarify handles page routes, static asset paths, client-side navigation, and raw content links consistently.

---

## Hiding pages

The current version does not provide a `hidden` frontmatter. To hide a page, simply do not add it to the explicit `tabs` configuration. The file still exists and can be accessed directly via its URL.
